## The idea

One question unlocks almost every tree problem:

> **What does a node return to its parent?**

Answer that before writing anything and the recursion writes itself. The base
case is what an empty subtree returns, and the body combines the two children.

<Snippet file="code/binary_trees.py" symbol="max_depth" title="The template, at its simplest" />

That is the entire shape. Height, node count, sum, "is this balanced", "are
these two trees identical" — all the same three lines with a different
combining step.

## When the return value is not the answer

Here is the thing that makes trees feel harder than they are. Sometimes **what
the parent needs is different from what the problem asks for.** The recursion
must return the former and record the latter on the side.

<Snippet file="code/binary_trees.py" symbol="diameter" title="Return depth, record the diameter" />

The parent can only extend a path *downward*, so what it needs is the depth
below a node. But the answer is the longest path *through* a node, which bends
and cannot be extended upward. Two different quantities, so: return the depth,
accumulate the answer in a `nonlocal`.

Once you see this, a whole tier of "hard" tree problems becomes routine.

<Snippet file="code/binary_trees.py" symbol="max_path_sum" title="The same shape, two wrinkles" />

Maximum Path Sum is diameter with two additions, and both are worth saying
aloud as you write them:

- `max(gain(child), 0)` — you may **decline** a negative branch. Taking it is
  never forced.
- The parent gets `node.val + max(left, right)`, only **one** side, because a
  path that used both children already bent and cannot continue upward.

Initialise the best to negative infinity, not zero. An all-negative tree has
an all-negative answer, and seeding with 0 quietly returns 0 for `[-3]`.

## BFS when the question mentions levels

<Snippet file="code/binary_trees.py" symbol="level_order" title="Level-order traversal" />

`for _ in range(len(queue))` is the whole trick. Capturing the queue length
*before* the inner loop snapshots exactly one level; without it the loop keeps
consuming nodes that were just added and you get a flat traversal with no
level boundaries.

This one loop, with tiny variations, answers level order, zigzag (reverse
alternate levels), right-side view (take the last of each level), and maximum
width.

## The six-line LCA

<Snippet file="code/binary_trees.py" symbol="lowest_common_ancestor" title="Lowest common ancestor" />

Worth staring at, because it looks like it cannot possibly be enough.

Read the return value as "*did this subtree contain either target, and if so
where's the highest relevant node*". If a node hears back from **both**
children, it is the meeting point. If only one side reports, pass that report
upward. The base case returns the node itself when it *is* a target — which
correctly makes a node its own ancestor.

## Pitfalls

- **Recursion depth.** Python's limit is 1000. A skewed tree with n = 10⁵
  blows it. Say so, and offer the iterative traversal with an explicit stack.
- **`if not node` versus `if node is None`.** A node with `val = 0` is falsy
  only if you wrote `if not node.val` by mistake — but be careful with the
  distinction on values.
- **Seeding a maximum with 0** when negatives are possible.
- **Forgetting a node is its own ancestor** in LCA. It is, unless the problem
  says otherwise.
- **`list.pop(0)` for a BFS queue** is O(n). Use `deque`.
- **Confusing height and depth.** Height is measured downward from a node,
  depth downward from the root. Problems use both; check which.

## Anchor walkthroughs

### Diameter of Binary Tree

**Clarify.** Is the diameter measured in **edges** or **nodes**? (Edges, on
LeetCode — so a two-node tree has diameter 1. Getting this backwards is an
off-by-one on every test.) Must the path pass through the root? (No, and that
is the point.)

**The naive attempt.** For every node, compute left height plus right height,
each in O(n) — that is O(n²). Worth stating, because it motivates the fix.

**The insight.** One traversal can do both: while computing the height of a
node, you already have both children's heights, so record `left + right` on
the way back up. O(n).

**Dry-run** `[1,2,3,4,5]`. At node 2, left height 1 and right height 1 → path
of 2. At node 1, left height 2 and right height 1 → path of 3. Answer 3, which
is the path 4→2→5→... no — 4→2→1→3. Trace it on the board; the point is that
the best path does not pass through the deepest leaf.

### Lowest Common Ancestor

**Clarify.** Are both nodes guaranteed present? (Usually yes — if not, the
algorithm needs a second pass to verify.) Is there a parent pointer? (If yes,
it becomes the intersection-of-two-linked-lists problem instead.) Is a node
its own ancestor?

**The insight.** Recurse, and let each node report what it found. Both sides
reporting means you are the meeting point.

**Why it terminates correctly:** once a node returns itself as the answer, its
ancestors see exactly one non-null child and pass it straight up unchanged. So
the first (deepest) meeting point survives all the way to the root.

**Follow-up:** the BST version, which is much easier — walk down, and the
first node whose value sits between `p` and `q` is the answer, in O(h) with no
recursion needed. Do not use the general algorithm when the BST version
applies; using the ordering is the point of the question.

### Binary Tree Maximum Path Sum

**Clarify.** Must the path contain at least one node? (Yes — so an all-negative
tree returns its largest single value, not 0.) Can the path start and end
anywhere? Does it have to be downward-only? (No, it may bend once.)

**The insight.** Diameter's structure with values instead of counts: return
the best downward gain, record the best bending path.

**The two wrinkles**, said aloud as you write them: clamp negative children to
zero, and pass only one side upward.

**Dry-run** `[-10, 9, 20, null, null, 15, 7]`. At 20: left 15, right 7, bend =
42, return 35. At −10: left is 9, right is 35, bend = 34, which loses to 42.
Answer 42 — the best path never touches the root, which is what makes the
`nonlocal` necessary.

**Then run `[-3]`** and confirm you get −3, not 0.
